# Фоновый ввод-вывод и virtual threads

LoveEssential использует Java 25 virtual threads для блокирующего ввода-вывода.
`VirtualIoExecutor` создаёт отдельный именованный virtual thread для каждой принятой
задачи. Семафоры сохраняют прежний бюджет: максимум 8 выполняемых операций и 256
ожидающих. При переполнении вызывающий поток не ждёт свободного места; `async` и
`asyncRun` возвращают Future с `RejectedExecutionException`.

На этот путь переведены конфиги и локализация, импорт/экспорт NPC, проверка папок
миров, чтение стартового набора и сетевой поиск скинов. Задачи передают неизменяемые
данные; работа с миром, сущностями, GUI и инвентарями возвращается через MainThread.
Изменять Bukkit-состояние внутри переданной I/O-функции нельзя.

SQLite уже использовал virtual threads. Его чтения ограничены 64 запросами, пулом
HikariCP на 3 подключения, а записи остаются последовательными с ограниченной
очередью: отдельные параллельные писатели не улучшают работу SQLite. Вычисление
пути NPC остаётся в ограниченном пуле platform threads: это CPU-работа.

## Завершение и отмена

- Все внутренние операции используют `LoveEssentialPlugin.async(Supplier)` или
  `asyncRun(Runnable)`. Переполнение и остановка завершают соответствующий Future.
- При штатном отключении I/O получает до 2 секунд на завершение принятых задач;
  затем оставшиеся owned Future отменяются, а потоки получают interrupt. Невыполненные
  задачи после отмены не запускают пользовательскую операцию. Перед прерыванием выполняемых задач сначала
  помечаются отменёнными все ожидающие: освободившееся разрешение не запускает
  следующую операцию в середине обхода отмены.
- SQLite закрывается после этой стадии, чтобы завершённая I/O-операция могла передать
  ему сохранение. Уже принятые записи SQLite завершаются по его собственной политике.
- Защита запуска не позволяет опубликовать открытый SQLite после начала отключения:
  поздно созданное хранилище закрывается самой загрузочной задачей.
- `ExecutorService io()` оставлен для совместимости. Расширениям рекомендуется новый
  API с отслеживаемыми Future: обычный `CompletableFuture.supplyAsync(..., io())` не
  передаёт исполнителю свой Future, и его отмену при принудительной остановке должен
  обеспечивать вызывающий код.

Interrupt не является транзакцией: неотменяемая сторонняя операция может закончиться
позднее. Отмена Future сама по себе не откатывает предметы, экономику или запись на диск.
Такие действия не объединяются в «последнее состояние» и не запускаются повторно.

## Проверка качества

Регрессии проверяют отдельные virtual threads, ограничение параллельности и приёма,
переполнение, штатное завершение, принудительную остановку с выполняемой и ожидающими
задачами, отмену вызывающим кодом и ограниченный срок ожидания. Интеграционная проверка
подтверждает, что отклонённый reload возвращает завершённый Future и сбрасывает busy.

Дополнительно воспроизведена потеря цены незавершённого revive при остановке: у
помогающего списывались 2 уровня из 5 и оставались 3. `Revive.close()` теперь вызывает
возврат до освобождения состояния, с учётом существующего `price.refund-on-stop`.
Тест проверяет возврат до 5 уровней и снятие принудительной позы.

Исправлен недетерминированный тест размещения столба: он выбирал произвольный
BlockDisplay из трёх уровней и иногда сравнивал верхний уровень с основанием
области ПКМ. Теперь проверка выбирает нижний уровень по Y, сохраняя проверку
совпадения основания модели и области нажатия.

Ускорение и сокращение heap не измерялись; изменение устраняет ошибки жизненного
цикла и меняет организацию исполнения, сохраняя прежние ограничения нагрузки.
